## 2. やった最適化

| 内容 | ねらい |
|---|---|
| Managed Stripping を **High** に（WebGL） | 使わないコードを強めに削り、wasm を小さくする。このプロジェクトのコードは `Assets/link.xml` で守る |
| IL2CPP のコード生成を **OptimizeSize** に（WebGL） | wasm を小さくする（実行速度はほぼ変わらない） |
| HUD の文字（スコア・残り時間）を、値が変わったときだけ作る | 毎フレームのメモリ確保をなくし、ブラウザでの GC によるカクつきを防ぐ |
| ゲージの文字（Lv・倍率・番号）を使い回す | 同上 |
| カメラが毎フレームシーンを探すのをやめる（`PlayerController.Active`） | 毎フレームの検索と配列の確保をなくす |
| 杵・Lv.3 シュートの当たり判定を `OverlapSphereNonAlloc` に | 当たり判定のたびの配列の確保をなくす |
| **F3** で fps を表示（`FpsOverlay`） | 公開版で 4 人対戦中の fps を測れるようにする |

設定は `Tools → Mochi Hockey → Apply WebGL Settings for GitHub Pages`（`WebGLPublishSettings.Apply`）でまとめて入る。

> 公開版で何かが動かなくなったら（ボタンが効かない、画面が出ないなど）、Managed Stripping が必要なコードまで削った可能性がある。
> その場合は、ブラウザの Console（F12）のエラーを Claude に伝える。`link.xml` に足すか、Stripping を Medium に下げる。

## 3. 入力遅延について（設計上の確認）

- 入力は Input System が毎フレームの最初（Update の前）に読み、`PlayerInputReader` → `PlayerController` が同じフレームの Update で速度を決める。
- 物理（FixedUpdate）でプレイヤーが動き、その結果が同じフレームの描画に出る。
- そのため、入力から画面に出るまでは 1〜2 フレーム（ブラウザの描画の待ちを入れても 3 フレーム以内）。体感で遅れを感じたら教えてください。

## 4. 公開版で確かめること（push のあと）

### fps（4 人対戦中）

1. 公開版を開き、ゲームパッドなどで 4 人参加して試合を始める（2 人でもよい。そのときは人数を書く）
2. **F3** を押すと、左上に `60 fps  16.7 ms  (worst 18.0 ms)` のように出る
   - 左から：平均 fps、平均のフレーム時間、0.5 秒の間でいちばん遅かったフレーム
3. 叩き合い・ダッシュ・シュート・ゴールなど、演出が多い場面で数字を見る
   - [ ] fps が 60 前後を保つ（58 以上が続けばよい）
   - [ ] worst がたまに 30 ms を超える程度（ずっと超えるならカクついている）
4. もう一度 **F3** で消える

> モニターが 60Hz より速い（120Hz・144Hz など）と、fps はそれに合わせて高く出る。その場合は 60 以上なら OK。

### ロード時間

1. F12 → **Network** タブ → **Disable cache** にチェック、回線は **No throttling**
2. Ctrl + Shift + R で読み込み直し、タイトル画面が出るまでの時間を見る（Network の下の「Load」や、ストップウォッチでよい）
   - [ ] 15 秒以内（ふだんの回線で）
3. 回線を **Fast 4G** にして同じことをする（参考）
4. 終わったら No throttling に戻し、Disable cache を外す

- [ ] Firefox で公開版を開き、タイトル → 試合 → 音 → フルスクリーンが動く
